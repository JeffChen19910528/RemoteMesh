# RemoteMesh 效能報告(Phase 13)

量測項目:連線建立時間、延遲、FPS、CPU、記憶體、頻寬、編碼延遲、輸入延遲、檔案傳輸速度、多 Session。
所有數字都由 `tests/RemoteDesktop.Performance.Tests` 實際量測,不是估算。

## 1. 量測環境與方法

- 機器:Intel Core Ultra 7 265K(20 邏輯核心)、63 GB RAM、Windows 11、.NET 10.0.12、Workstation GC
- 以 Release 組態執行:`dotnet test tests/RemoteDesktop.Performance.Tests -c Release`
- 延遲以 `Stopwatch` 量測;CPU 為行程 CPU 時間 ÷ 經過時間(100% = 滿載一個核心);工作集每 20 ms 取樣取峰值
- 匯出數字到檔案:設定環境變數 `RM_PERF_OUT=<路徑>`;大檔案大小以 `RM_PERF_FILE_MB` 調整(預設 256)

**這些數字的限制(請務必一併閱讀)**
1. 全部在**同一個行程內**以記憶體傳輸量測,沒有真實網路延遲、頻寬與封包遺失。延遲數字代表「軟體本身的處理成本」,不是使用者實際感受到的延遲。
2. 螢幕擷取是合成的測試畫面,沒有真實 OS 擷取與 GPU 成本;編碼器是軟體參考編碼器,不是 H.264/VP9/AV1。
3. CPU 數字同時包含收發兩端與測試框架本身(同一行程)。
4. 單一機器、單次執行,數字會有數十個百分點的波動;測試中的門檻刻意寬鬆,目的是抓出退化,不是驗收絕對效能。
5. `sessions` 單 Session 那一列與第一個串流列的工作集偏高(約 +190–250 MB),是因為測試場景的 20 張 8 MB 畫面在該測試內才首次產生,不是串流本身的記憶體用量。

## 3. 發現的瓶頸與處理

### 3.1 頻寬:參考編碼器完全無法達到各畫質檔位的位元率預算
Deflate 編碼器每幀獨立、無損壓縮整個畫面。實測:

| 檔位 | 解析度@FPS | 每幀大小 | 需要頻寬 | 檔位預算 |
|---|---|---|---|---|
| VeryPoor | 960×540@15 | 498 KiB | 61 Mbit/s | 0.8 Mbit/s |
| Poor | 1280×720@20 | 882 KiB | 145 Mbit/s | 2 Mbit/s |
| Good | 1600×900@30 | 1377 KiB | 338 Mbit/s | 5 Mbit/s |
| Excellent | 1920×1080@60 | 1976 KiB | 971 Mbit/s | 10 Mbit/s |

**處理**:新增 `TileDeltaVideoEncoder/Decoder`(仍是無損參考編碼器),把畫面切成 64×64 區塊,只傳送有變化的區塊;含週期性關鍵幀、解析度變更與要求時的關鍵幀、序號偵測丟幀並要求關鍵幀、完整的不可信輸入驗證(21 項差分編碼專屬測試,含隨機修改的性質測試)。

| 情境(720p@20) | Deflate | 差分編碼 | 編碼耗時 |
|---|---|---|---|
| 桌面閒置(只有游標移動) | 144.6 Mbit/s | 0.6 Mbit/s(**−99.6%**) | 6.9 → 0.8 ms |
| 一般操作(約 8% 畫面變化) | 141.7 Mbit/s | 6.9 Mbit/s(**−95%**) | 6.9 → 1.5 ms |
| 全螢幕影片(每個像素都變,隨機雜訊) | 622 Mbit/s | 622 Mbit/s(無差異) | 約 28–30 ms |

**未解決**:一般操作的 6.9 Mbit/s 仍高於 Poor 檔位的 2 Mbit/s 預算,影片類內容完全沒有改善。無損壓縮在原理上做不到,這類內容需要**有損的真實影片編碼器(H.264/VP9/AV1)**,需要原生函式庫或硬體編碼,尚未整合。`IVideoEncoder` 介面已預留,但這是上線前最大的效能缺口。

### 3.2 GC 壓力:每幀配置多個大物件堆積(LOH)緩衝區
拆解 720p 每幀成本(最佳化前):Deflate 6.8 ms、縮放 2.5 ms、解壓縮 3.1 ms、加密+送出 1.35 ms、封包化與重組 0.2 ms。**20 次編碼就觸發 7 次 gen-2 GC**(每三幀一次),因為每幀配置縮放緩衝區、串流增長、多次複製等多個大於 85 KB 的陣列。

**處理與效果**(Deflate 路徑,720p@20):

| 項目 | 之前 | 之後 |
|---|---|---|
| 縮放耗時(逐像素整數除法 → 預先計算欄位表) | 2.5 ms | 1.1 ms |
| 20 次編碼期間 gen-0 / gen-2 GC | 7 / 7 | 0 / 0 |
| 每幀配置 | 18.6 MB | 7.0 MB |
| 串流 CPU | 56% 核心 | 50% 核心 |
| 端到端處理延遲 p95 | 19.3 ms | 11.8 ms |

做法:縮放與解碼輸出改用 `ArrayPool` 租用(`CaptureFrame.Owner`,由接收端在繪製後釋放)、輸出串流預留容量並去掉多餘複製、解碼器直接從呼叫端陣列讀取、重組器以單次配置串接(取代逐位元組的 LINQ)、`SecureChannel` 直接加密到最終封包(每個區塊由 3 份配置降為 1 份)。
改用差分編碼後(同為 720p@20):每幀配置 1.0 MB、CPU 25% 核心、頻寬 10.4 Mbit/s。

**契約變更**:`IFrameRenderer.RenderAsync` 收到的畫面像素是租用的,只在呼叫期間有效;要保留像素的繪製器必須自行複製。

### 3.3 資源上限
盤點時發現下列上限缺漏或寫死,已補上並加測試:

| 上限 | 位置 | 預設 |
|---|---|---|
| Maximum Frame Size | `FrameReassembler`(依「實際收到的位元組」計,而非封包宣告的區塊數) | 單幀 64 MB;未完成幀總量 256 MB,超過就丟最舊的 |
| Maximum Sessions | `SessionSecurityOptions.MaxTotalActiveSessions` | 10,000;另有每設備 8、每目標待處理 5 |
| Relay 同時配對數 | `RelayOptions.MaxConcurrentPairings` | 10,000(容量不足時不消耗 token) |
| Maximum Bandwidth | `RelayOptions.MaxBytesPerSecond` | 每方向 25 MB/s |
| Maximum Message Size | SignalR 64 KB;Relay 1 MB;檔案訊息約 70 KB;剪貼簿 1 MB/10 MB | — |
| Maximum File Size / Transfer Rate | `FileTransferHostOptions` | 1 GB;速率可設 |
| Relay 連線速率 | `RelayOptions.ConnectionsPerMinutePerAddress` | 每位址每分鐘 60(原本寫死在 Program.cs,現在可設定,因為公司 NAT 後多人共用一個位址) |

另外補上兩個與資源相關的缺口:**Session 到期**(`ExpiresAt` 之後原本沒有任何東西會結束 Connected 的 Session,Relay 會一直轉送)現在由背景清掃結束、撤銷 token 並中斷 Relay;**已結束的 Session** 原本永遠留在記憶體,現在超過保留期(預設 1 小時)後清除。

### 3.3b 有損編碼(JPEG 分塊)與碼率控制

3.1 的瓶頸現在有一個可用的緩解:`TileDeltaJpegEncoder` 只送有變動的區域,而且變動區域以 JPEG 壓縮(Windows 用系統內建的 GDI+,不自己寫影像程式);`RateController` 依實測的輸出碼率與「送出一幀要等多久」(連線塞住的訊號)在畫質階梯上升降。以下是**這台開發機的真實 1920×1080 桌面**(只在記憶體量測,未儲存):

| 情境 | 結果 |
|---|---|
| 桌面靜止 | 不送任何東西(8 秒真實連線共 227 KB,平均 0.23 Mbit/s,主要是第一張關鍵幀) |
| 一張關鍵幀 | 約 219 KB,編碼約 5 ms,解碼約 0.7 ms |
| 整屏持續變動(每幀都卷動),無損 | 約 418 KB/幀 = **68.6 Mbit/s**(20 fps) |
| 整屏持續變動,JPEG 品質 80 | 約 221 KB/幀 = **36.3 Mbit/s**(只省約一半) |
| 同上,各檔位(20 fps 換算) | 100% q30:19.5 · 75% q50:16.1 · 50% q50:8.4 · 50% q30:6.4 Mbit/s |
| 6 Mbit/s 的慢線、預算 5 Mbit/s、整屏持續變動 | 最後 4 秒穩定在 **5.0 Mbit/s**,平均約 5 fps,最終停在「75% 大小、品質 50、15 fps 上限」 |

**結論(誠實版):** 一般操作(打字、拖視窗、局部捲動)很省;**整屏持續變動時,JPEG 沒有幀間預測,畫面會變軟、而且只有約 5 fps**(在 5 Mbit/s 預算下)。要在這種情境接近 AnyDesk/TeamViewer 的順暢度,需要有動態補償的真正影片編碼器(H.264 等)。這一步沒有做。

量測時發現並修掉的問題:發送端從不釋放撷取的緩衝(每秒約 160 MB 大物件配置);限速從「上一幀送完」起算導致實際幀率遠低於設定;被拒絕的連線要等滿逾時才發現。碼率預設 6000 kbps,可由 `Agent:VideoBudgetKbps` / 界面 `settings.json` 的 `VideoBudgetKbps` 調整。

### 3.4 沒有瓶頸的項目(已量測確認)
- 加密通道、輸入驗證、Relay 轉送、設備註冊、連線建立都在微秒到個位數毫秒等級,不是效能風險。
- 大檔案傳輸確實是串流:256 MB 的檔案工作集只增加 4–17 MB。每個 64 KB 區塊仍有約 5–6 份複製(配置約檔案大小的 6 倍),吞吐量已足夠(182–290 MB/s),沒有進一步最佳化。

## 5. 尚未量測 / 後續工作
1. **真實網路**:延遲、頻寬變化、封包遺失下的行為(適應性畫質控制器的實際回饋、重連),需要網路模擬環境。
2. **真實擷取與編碼**:OS 擷取成本、硬體編碼、4K/60 FPS。
3. **真實影片編碼器**(見 §3.1)。
4. **伺服器長時間負載**:數千個同時 Session 的數小時 soak test;目前狀態都在記憶體,PostgreSQL 持久化後需重測。
5. **TLS 成本**:測試使用行程內傳輸,沒有 TLS 握手與加密開銷。
6. 差分編碼器的關鍵幀要求目前以 `KeyframeNeeded` 事件與 `RequestKeyframe()` 提供,尚未接到 Control 通道的實際訊息(由 Session 協調器負責);週期性關鍵幀(預設每 2 秒)會限制失去同步的最長時間。
