# 安全

完整分析見 [THREAT_MODEL.md](THREAT_MODEL.md)。本文件是給部署者與開發者的操作面總覽。

## 1. 安全原則

Secure by Default、最小權限、明確授權、零信任的 Session 建立、傳輸加密、金鑰隔離、可稽核。具體落實:

| 原則 | 實作 |
|---|---|
| 預設安全 | 預設只授予檢視;剪貼簿預設關閉;非開發環境強制 TLS;信任轉送標頭預設關閉;所有限制都有保守的預設值 |
| 最小權限 | 九個獨立權限位元;長期信任不得含重啟/關機;權限逐訊息檢查、撤銷即時生效 |
| 明確授權 | 目標端使用者逐次核准(或 OTP/預先信任);請求逾時失效;狀態轉換用 compare-and-set |
| 零信任 | 設備以私鑰證明身分;所有輸入視為不可信並驗證;伺服器與 Relay 看不到內容 |
| 傳輸與內容加密 | TLS + 端到端 AES-256-GCM(序號、AAD、重放視窗、金鑰紀元) |
| 金鑰隔離 | 私鑰只存在簽章器/金鑰儲存內:Windows 以 DPAPI 保護,Unix 以 0600 檔案權限 |
| 可稽核 | 連線請求、核准、權限授予、開始/結束、Relay 開始/結束、暫停/恢復/到期、驗證失敗、限流觸發 |

## 2. 威脅對應的防護

| 必須防止 | 防護 |
|---|---|
| Unauthorized Remote Access | 設備認證 + 使用者核准 + 狀態機;沒有經過核准不可能進入 `Connected` |
| Brute Force Device IDs | 未知設備查詢額度、統一錯誤訊息、請求速率限制 |
| Session Hijacking | 參與者檢查、單次使用綁定 token、角色配對的 Relay、compare-and-set |
| Replay Attacks | 註冊挑戰單次使用;通道序號視窗;金鑰紀元;token 單次使用 |
| Credential Theft | 私鑰不外流、不記錄;token 短效且單次使用;token 走標頭不走 URL |
| Unauthorized Persistence | 沒有任何背景自動連線;Session 有到期時間並由清掃強制 |
| Hidden Remote Control | 目標端必須核准(或事先明確信任);稽核紀錄完整 |
| Rate Limiting / Lockout | 註冊失敗、OTP、連線請求、未知查詢、Relay 連線、恢復嘗試各自限流與鎖定 |
| Audit Logging | 見上 |

## 3. 安全部署檢查表

- [ ] 使用 TLS(直接由 Kestrel 提供憑證,或由反向代理終止 TLS)。非開發環境若請求不是 HTTPS,伺服器對**所有端點(僅 `/health` 例外,供探針使用)**回 400「TLS required.」(信令 hub 會傳送 Session 與恢復 token,不能走明文);伺服器知道自己的 HTTPS 連接埠時會改為導向。
- [ ] 若在反向代理後面:設定 `RemoteMesh:ForwardedHeaders`,**只列出實際的代理位址**;否則所有使用者共用代理位址,限流與鎖定會一次影響所有人。代理必須**覆寫**而不是附加 `X-Forwarded-For`。
- [ ] 代理與存取日誌**不要記錄請求標頭**(Relay token 在 `X-Relay-Token`)。
- [ ] `appsettings*.json` 不放任何祕密(憑證密碼、連線字串…);用憑證存放區、環境變數或祕密管理服務。程式有測試確認隨附設定檔不含憑證類欄位。
- [ ] 以專用的低權限帳號執行(提供的 Windows 安裝腳本使用 `NT SERVICE\RemoteMeshServer`;systemd 單元已加上沙盒)。
- [ ] 防火牆只開放 HTTPS 連接埠。
- [ ] 依你的規模調整 `RemoteMesh:*` 限制(見 [CONFIGURATION.md](CONFIGURATION.md));設定錯誤會讓伺服器啟動失敗,而不是悄悄使用不安全的值。
- [ ] 在伺服器前面部署網路層防護(DDoS、WAF);應用層限制只保護應用,不取代它們。
- [ ] 目前伺服器狀態在記憶體:了解重啟會中斷所有 Session、稽核不持久也不防竄改。**在持久化稽核完成前,不要把本系統當作需要鑑識等級稽核的環境。**

## 4. 開發規則

- 不自創密碼學;不重新實作 ICE/STUN/TURN/TLS。
- 不記錄:私鑰、密碼、Session 祕密、剪貼簿內容、檔案內容(輸入事件的鍵碼與座標同樣不記錄)。
- 所有輸入事件必須經過 Session 認證與權限驗證才能注入。
- Session token:短效、不可預測、單次使用、綁定設備、可撤銷。
- Relay 不解密。

## 5. 已知的重大限制

這些是**設計層級**的取捨,尚未處理(詳見 THREAT_MODEL.md §4 與 RELEASE_READINESS.md):

1. **對方公鑰的首次接觸只靠「首次使用即信任」**:客戶端已經把見過的設備金鑰釘選在本機,金鑰之後被換掉會中止連線;兩邊畫面也顯示安全碼供核對。但**第一次接觸時若伺服器就換掉金鑰、而使用者沒有核對安全碼,仍然抓不到**。
2. **沒有前向保密**:工作階段金鑰來自靜態 ECDH。設備私鑰外洩後可解密已錄下的舊流量。要改用成熟協定的臨時金鑰(Noise 或 TLS 1.3 雙向認證),不可自行設計。
3. **沒有設備撤銷與金鑰輪替**:首次註冊釘住公鑰,之後無法重新註冊同一個 DeviceId(換機或私鑰外洩)。
4. Unix 上私鑰只靠檔案權限保護(未整合 libsecret / kernel keyring)。
5. 狀態與稽核都在記憶體。

## 6. 回報漏洞

目前**尚未設定正式的安全聯絡管道**。在公開發行前請先建立(例如專用信箱或私有的漏洞回報流程),並更新本節。在此之前,請透過專案維護者的私人管道回報,不要公開張貼未修正的漏洞細節。

## 7. 審查範圍

Phase 12 的審查是**內部審查**:逐模組閱讀程式碼、威脅分析,並以 63 個攻擊情境測試(含「把防護拿掉、測試必須失敗」的變異檢查)驗證修正。**沒有進行外部滲透測試或第三方程式碼稽核**,正式發行前建議進行。
